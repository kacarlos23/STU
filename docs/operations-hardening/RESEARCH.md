# Operations and hardening research

## Scope selected for the first Phase 6 delivery

The first missing operational capability is backup management. The existing platform already has append-only audit records, API rate limits, health checks, HTTPS headers, persistent data-protection keys, and a PWA policy that does not cache private API data.

This delivery therefore adds the complete backup control loop requested for the MVP:

- a weekly schedule, enabled by default and editable only by the global administrator;
- an on-demand backup action in the isolated administration portal;
- persistent execution history with queued, running, completed, and failed states;
- PostgreSQL custom-format archives, size and SHA-256 integrity metadata;
- configurable retention without deleting the append-only execution history;
- download restricted to the global administrator;
- audit records for schedule changes and manual requests;
- a restore runbook and automated tests.

## Technical findings

- PostgreSQL 18 `pg_dump` creates a consistent export while the database remains available to readers and writers.
- The custom archive format is compressed by default and is intended for `pg_restore`, which makes it a practical MVP format for full-database recovery.
- The worker must use the PostgreSQL 18 client because client/server major-version compatibility matters. The official PostgreSQL Apt repository provides `postgresql-client-18` for the Debian bases used by the .NET image.
- Credentials must not be placed in process arguments or logs. The worker passes the password through the child-process environment and constructs every argument separately.
- Archives are written first as a temporary file and are renamed only after `pg_dump` exits successfully. This prevents incomplete files from appearing as downloadable backups.
- The shared operations volume already mounted by the API and worker is suitable for the first deployment. Off-host replication remains a later hardening item because a server-local copy does not protect against total host loss.

## Security decisions

- All backup API routes use the existing global-administrator policy, rate limiting, authenticated cookies, and CSRF checks for mutations.
- File names are generated by the server. A database value is never accepted as an arbitrary filesystem path.
- Downloads use a resolved path constrained to the configured backup directory.
- Error details returned to the UI are summarized and never include the database password or full connection string.
- Retention removes only archive files beyond the configured count. Backup execution records remain in the database for traceability.

## Deferred Phase 6 work

- independent off-host copy and encryption-key custody;
- automated restore rehearsal in an isolated database;
- external alert delivery after an institutional channel is selected;
- load, accessibility, and security validation for the pilot.

## Monitoring delivery research

The next Phase 6 slice is basic operational monitoring. ASP.NET Core explicitly distinguishes liveness (the process is running) from readiness (the application can serve traffic) and supports selecting readiness checks by tags. The STU will keep the existing lightweight liveness endpoint and add readiness checks for the database, shared operations storage, and worker heartbeat.

The global administrator needs more context than a binary health response. A protected monitoring snapshot will therefore combine the same infrastructure signals with backup recency, recent backup failures, stalled operation jobs, and recent asynchronous failures. Alerts are computed from existing operational state rather than copied into another mutable alert table.

The worker heartbeat is persisted at a controlled interval. This detects a worker that has stopped even when the API and database remain online, without creating a database write on every three-second processing poll.

External delivery is deliberately deferred: no institutional e-mail, webhook allowlist, or incident-management channel has been selected. The public readiness endpoint is vendor-neutral and can already be polled by infrastructure owned by the municipality.
